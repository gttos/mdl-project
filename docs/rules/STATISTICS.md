<a id="metricas"></a>
## Métricas y cálculos

- **RP-EST-001.** Las estadísticas son de sólo lectura y se calculan en la API exclusivamente con la estructura perteneciente a la cuenta autenticada. Las aplicaciones presentan el resultado recibido y no recalculan ratios, medias ni distribuciones.
- **RP-EST-002.** La beta ofrece un único dashboard personal calculado sobre todo el historial elegible de la cuenta.
- **RP-EST-015.** El dashboard de la beta se compone exactamente de: resumen (`summary.winRate`, `summary.averageSatisfaction`, `summary.topDucky`, `summary.actualStatus`); match (`match.byStatus`, `match.firstBySituation`); momento actual (`moment.activeCrushes`, `moment.bySituation`); distribución de satisfacción (`satisfaction`); perfil de valoraciones (`attraction`); rasgos físicos (`physical`); zodíaco (`zodiac`); países (`countries`); y Ducky (`ducks`). Cada sección variable informa `status`, `value`, `sample.used` y `sample.required`.
- **BR-12.01.** Las valoraciones y la satisfacción utilizan la escala entera de 1 a 5. La API convierte esos IDs a sus valores numéricos para calcular estadísticas.
- **RP-EST-003.** La API redondea medias y porcentajes a dos decimales en el contrato. En el dashboard, las aplicaciones muestran los porcentajes como enteros y las medias de escala 1–5 con un decimal; los conteos representan cantidades reales y se muestran como enteros. Esta presentación sólo formatea el valor publicado y nunca recalcula ratios, medias ni distribuciones.
- **RP-EST-004.** Win rate = 100 × Crushes históricos elegibles con `match_status_id = MATCH` / Crushes históricos elegibles con `match_status_id` resuelto (`MATCH + NO_MATCH`). Cuenta Crushes distintos, nunca supera 100% y excluye `UNKNOWN` del denominador. `match.byStatus` informa por separado los tres conteos `MATCH`, `NO_MATCH` y `UNKNOWN`.
- **RP-EST-005.** Denominador cero implica no disponible, no 0% medido.
- **RP-EST-006.** La satisfacción media utiliza las experiencias elegibles y sus valores de 1 a 5. Sin experiencias elegibles, el resultado es nulo.
- **RP-EST-007.** El Ducky predominante es la única categoría con mayor frecuencia entre los Crushes elegibles. Sin muestra o cuando dos o más categorías empatan en la frecuencia máxima, no existe un Ducky predominante y el resultado es nulo; nunca se escoge uno mediante orden de ID, antigüedad ni otro desempate arbitrario.
- **RP-EST-008.** `actualStatus` cuenta períodos vivos cuya `current_situation_id` es `8 RELATIONSHIP`: cero produce `single`, uno produce `in_relationship` y más de uno produce `multiple_relationships`.
- **RP-EST-009.** `activeCrushes` cuenta Crushes con un período vigente vivo. `bySituation` distribuye esos períodos por `current_situation_id`; no existe una agrupación por fase o etiqueta interna.
- **RP-EST-010.** Sin Crushes activos no archivados, `moment.status` es `empty` y `moment.value` es nulo. Con al menos un Crush activo no archivado y ningún período vivo elegible, `moment.status` es `available` y `activeCrushes` vale cero.
- **RP-EST-011.** Match utiliza las proyecciones `match_status_id` y `first_match_situation_id` del Crush; `firstBySituation` cuenta cómo se produjo el primer match únicamente entre las situaciones 5–9. Satisfacción utiliza `satisfaction_id`; Ducky utiliza `ducky_id`; atracción utiliza las cuatro valoraciones y `rate_global`; rasgos físicos utilizan `height_id`, `eye_color_id`, `hair_color_id`, `body_type_id` y `skin_color_id`; zodíaco utiliza `zodiac_id`; y países utilizan `country_id`. El dashboard sólo calcula esas dimensiones con los campos estructurales indicados. Cuando una aplicación acompaña un valor de catálogo con nombre, icono o glifo, todos representan exactamente el mismo ID publicado; no desplaza, sustituye ni deduce categorías.
- **RP-EST-012.** Cuando una métrica no tiene datos suficientes, la API devuelve la sección con su estado y muestra correspondientes, con `value` nulo cuando corresponda. La aplicación distingue ese estado de una carga en curso o un error.
- **RP-EST-013.** Toda comparación, cobertura o indicación de confiabilidad se basa en valores calculados y publicados por la API. La aplicación no completa valores ausentes ni fabrica explicaciones.
- **RP-EST-014.** Durante carga o error se conserva la estructura visual de la pantalla, se identifica el estado y se ofrece una acción de reintento comprensible.
- **RP-EST-016.** Toda métrica basada en observaciones utiliza `sample.required = 1`: con al menos un registro elegible se calcula y presenta el resultado junto con `sample.used`; no se bloquea por alcanzar un umbral arbitrario mayor. Con cero registros aplica el estado vacío o el valor nulo definido para esa métrica. Los conteos y estados estructurales de RP-EST-008..010 conservan su semántica propia y tampoco se ocultan por tamaño de muestra.
- **RP-EST-017.** Las métricas históricas —win rate, satisfacción, Ducky, match, primer match y distribuciones— incluyen los Crushes activos y archivados de la cuenta porque archivar conserva la ficha y su historia. Las métricas del momento actual —`activeCrushes`, `bySituation` y `actualStatus`— utilizan únicamente Crushes activos no archivados. Los Crushes eliminados o seudonimizados quedan fuera de ambos alcances.
- **RP-EST-018.** El dashboard es una superficie descriptiva y visual: informa valores, conteos, porcentajes, promedios, distribución, base y respaldo del dato sin inferir gustos, personalidad, causas, recomendaciones ni conclusiones narrativas sobre la persona. Puede usar un tono cercano, pero cada título y subtítulo describe únicamente el dato observado. En particular, la distribución Ducky se presenta como los tipos que más aparecen entre los Crushes, nunca como tipos «favoritos» o «preferidos» si la API no publica esa preferencia. Un informe futuro generado con IA será una función separada, con reglas y contrato propios; el dashboard no adelanta esa interpretación ni publica perfiles inferidos.
- **RP-EST-019.** Toda media, porcentaje, distribución o categoría predominante publica una base calculada por API con `used`, `eligible`, `required`, `coveragePercentage` y `supportLevel`. `used` es la cantidad de observaciones que contribuyen al valor; `eligible` es el universo de registros que podría haber contribuido; `coveragePercentage = 100 × used / eligible`, redondeado conforme a `RP-EST-003`. `required` conserva únicamente el umbral de disponibilidad de `RP-EST-016` y nunca se presenta como denominador. Con `eligible = 0` la métrica queda vacía y no muestra semáforo. Los conteos y estados exactos del momento actual no llevan nivel de respaldo.
- **RP-EST-020.** El nivel de respaldo es determinista y combina tamaño absoluto y cobertura. Es `low` cuando `used < 10` o `coveragePercentage < 50`; es `high` únicamente cuando `used >= 30` y `coveragePercentage >= 80`; en cualquier otro caso es `medium`. El nivel describe cuánto dato sostiene el resultado, no certifica verdad científica, causalidad, representatividad externa ni estabilidad futura.
- **RP-EST-021.** Los campos opcionales se calculan por dimensión. Una valoración `null` no vale cero ni reduce artificialmente el promedio: queda fuera del numerador y del promedio, pero el Crush continúa dentro de `eligible`. Belleza, conexión emocional, personalidad, atractivo sexual y global publican cada uno su propio `used`, cobertura y nivel; una dimensión sin observaciones devuelve valor nulo. La misma regla por dimensión se aplica a cada rasgo físico y al zodíaco.
- **RP-EST-022.** iOS presenta el respaldo mediante un punto de color acompañado siempre por texto localizado: rojo «Pocos datos» para `low`, amarillo o ámbar «Base media» para `medium` y verde «Base amplia» para `high`. El color nunca es la única señal. Las filas muestran primero el valor estadístico y su conteo sobre el denominador real de cálculo —por ejemplo `50 % · 1 de 2`—; la tarjeta muestra aparte `used de eligible` cuando existen datos opcionales ausentes.
- **RP-EST-023.** Una dimensión física publica la distribución observada y todas las categorías que empatan en la frecuencia máxima. Nunca escoge una mediante orden de ID. El dashboard muestra una fila compacta por dimensión con su nombre visible, hasta tres iconos de líderes superpuestos y `+N` cuando haya más, además de nombres, porcentaje, conteo y estado «Empate» cuando corresponda. Un icono nunca sustituye el texto del rasgo. `summary.topDucky` conserva la semántica de `RP-EST-007`; las distribuciones de Ducky, zodíaco y países muestran todas sus filas observadas.
- **RP-EST-024.** Cada tarjeta que muestre respaldo ofrece una única ayuda accesible «¿Qué indica el color?», no una explicación repetida por fila. La ayuda define los tres niveles, aclara que el valor sigue siendo real aunque tenga pocos datos y explica cómo aumentar el respaldo completando los perfiles o experiencias correspondientes. Puede enlazar a la navegación existente para completar datos, pero no crea recomendaciones personales ni un recorrido paralelo.
- **RP-EST-025.** El dashboard permanece compacto y no incorpora en esta iniciativa las futuras pantallas de desglose. No muestra una navegación inerte ni promete detalle inexistente. El contrato físico conserva las distribuciones observadas necesarias para que una feature posterior pueda construir el detalle; incluir categorías con cero observaciones, análisis narrativo o comparación temporal requerirá su propio alcance.

<a id="metricas-excluidas"></a>
## Métricas excluidas

- **BR-12.02.** El dashboard, la API de estadísticas y sus presentaciones excluyen rankings competitivos de Crushes o cuentas, body count, predicciones de fracaso de un vínculo activo, percentiles de superioridad, valor de mercado y seguimiento individual de revisitas o ghosting.

<a id="entre-cuentas"></a>
## Alcance entre cuentas

- **RP-FUT-002.** Las estadísticas de la beta son personales: cada dashboard utiliza únicamente datos de su cuenta propietaria y no combina datos de distintas cuentas.
- **RP-FUT-003.** La estructura conservada tras una baja permanece fuera del dashboard personal y de cualquier consulta individual. Producto aprueba como función futura las estadísticas agregadas entre cuentas: incluirán, entre otros cortes que se definan, porcentajes de resultados relacionales para combinaciones de signos y patrones agrupados por país sobre países más presentes entre los Crushes, países más presentes entre los match y rasgos estructurales más frecuentes. Esta decisión funcional autoriza conservar dormantes el schema y los modelos reservados para esos resultados; no autoriza todavía calcularlos, poblarlos ni exponer resultados no vacíos. La activación requiere contrato de producto, población elegible, umbrales de agregación y supresión, actualización y retención, además de aprobación Legal. La infraestructura reservada no se elimina sólo por permanecer inactiva durante la beta.

Las proyecciones de match y primer match pertenecen al [Crush](CRUSH.md#match). Estadísticas las consume como estructura ya resuelta y no reconstruye la historia de períodos e hitos.
